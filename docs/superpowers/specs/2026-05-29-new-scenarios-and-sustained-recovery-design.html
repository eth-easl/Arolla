Design — 5 New Prototype Scenarios, Sustained-Recovery Metric & HTML Report

Date: 2026-05-29  ·  Status: params & structure approved; ready for implementation plan.

Goal

Broaden the prototype benchmark from 25 → 30 scenarios, fix a known weakness in how “recovery” is measured, and produce a standalone HTML report of the results (not a plot-viewer change).

  1. Recovery redefinition. The current recovery_sec marks recovery at the first single-second crossing of 95% success rate, so a run that briefly touches 95% and then collapses (metastable) still gets an optimistic finite recovery time. Add a robust sustained recovery metric.
  2. +2 alternate-service scenarios. Run the post-cart-stress pattern on two structurally different targets (productcatalogservice, paymentservice) to show the retry-amplification dynamics are not cart-specific.
  3. +3 multi-spike scenarios. Run post-cart-stress on cartservice with two fault spikes to test whether surviving the first spike leaves the system worse off so the second spike traps it (“can it recover twice?”).
  4. HTML report. A report builder reads the raw sweep outputs and emits an HTML report (+ a sibling assets folder of PNG/CSV) under outputs/proto-report.

Non-goals: retuning the existing 25 scenarios; changing the retry-control policies; altering archived outputs/ results; any change to the Next.js plot-viewer.

Policies under test (4)

Every new sweep run and the report compare exactly four policies:

no-control   envoy-retry-budget   arolla   rb-rl-v5

(circuit-breaker and the older RL variants v1–v4 are dropped from the new sweep; v5 is the representative RL policy.)

Part 1 — Sustained-Recovery Metric

Current behaviour (the problem)

  • analyze.py:recovery_time_sec → first post-fault second where smoothed success rate ≥ 95% absolute. Single-crossing ⇒ optimistic on metastable runs.
  • classify_runs.py adds a final-30s-window guard, but it only inspects the last 30 s, so a run that oscillates through the middle of recovery yet lands well is still mislabeled recovered.

New definition

Add a metric sustained_recovery_sec (the existing recovery_sec is left untouched for back-compat and old-vs-new comparison):

sustained_recovery_sec = the earliest t ≥ fault_end such that, for every 1-second bucket in the window [t, t + W] (W = 30 s), the smoothed series satisfy both:
  • success rate ≥ 0.95 × prefault_SR (relative)
  • goodput ≥ 0.90 × prefault_goodput (relative)
sustained_recovery_sec = t − fault_end. If no such window exists within the captured recovery+cooldown span → null (treated as not-recovered / metastable).

Rationale (all confirmed with the researcher):

  • Relative thresholds are load-independent; pre-fault SR genuinely dips at the 1600–1800 RPS scenarios where an absolute 95% bar is unfair.
  • Both SR and goodput: SR alone misses load-shedding policies that keep SR high on the few admitted requests while goodput stays on the floor.
  • W = 30 s reuses the existing FINAL_WINDOW_SEC constant; long enough to be confident, short enough to detect inside a 60 s inter-spike gap.
  • Additive, not a replacement: archived runs are never relabeled.

prefault_SR / prefault_goodput are the means over the pre-fault window ([t_warmup_end, t_fault_start)).

Multi-spike awareness

timeline.json already records per-spike timestamps (t_spike_<i>_actual_start/end, num_spikes). For multi-spike runs the metric is computed per spike:

  • After spike i < N: search [t_spike_i_end, t_spike_{i+1}_start).
  • After the final spike N: search [t_spike_N_end, t_recovery_end].

Output: per-spike values (sustained_recovery_sec_spike1, …_spike2) plus an overall label recovered_twice | recovered_once | never.

60 s gap caveat: with W = 30 s, the first recovery only “counts” if success climbs back within ~30 s of spike-1 clearing. For the hardest scenario the system may still be climbing when spike 2 lands — a legitimate result (“could not fully recover once before the next hit”) that must be annotated (recovered_once = false), not silently dropped.

Where it lands

A single shared helper holds the canonical computation so the per-run analyzer and the report builder never diverge. No plot-viewer / healthFromTimeseries.ts / aggregate_for_viewer.py changes.

FileChange
prototype/experiments/sustained_recovery.py (new) Canonical sustained_recovery(...) over per-second SR/goodput + phase/spike boundaries. Computes from raw timeline.json + client-metrics CSVs so it works on old runs too. Unit-tested.
prototype/experiments/analyze.py Emit sustained_recovery_sec (per-spike when num_spikes>1) into summary.csv, via the shared helper.

Unit coverage uses synthetic series: clean recovery, oscillate-then-collapse, sheds-load (high SR / low goodput), and multi-spike recover-once-then-trap.

Part 3 — Sweep Driver & Output Layout

Output root

All new runs go under outputs/proto-report/ (gitignored like the other output roots).

Scenario list

The canonical sweep_scenarios.csv only carries id,rate_rps,fault_duration,fault_rate,default_label. The 5 new scenarios need per-scenario client profile, fault manifest, num_spikes, inter_spike_gap, so add a richer sweep_scenarios_ext.csv:

id,client_profile,fault_manifest,rate_rps,fault_duration,fault_rate,num_spikes,inter_spike_gap,default_label
MS1,post-cart-stress-open,cartservice-75pct,1200,20,75,2,60,Recovered

The full set of 30 = the canonical 25 (read from sweep_scenarios.csv) + these 5.

Driver changes (run_full_sweep.sh or a focused variant)

  • Run exactly the 4 policies: a single run-experiment.sh call for no-control,envoy-retry-budget,arolla plus one RL call for rb-rl-v5 (rename envoy-retry-budget/ → rb-rl-v5/, merge into the scenario summary — reuse the existing v1–v3 merge machinery, retargeted to v5).
  • Read both sweep_scenarios.csv (cart, single-spike) and sweep_scenarios_ext.csv (per-row profile / fault manifest / spikes / gap).
  • 3 repeats. Output layout: 
    outputs/proto-report/<sweep_ts>/run{1,2,3}/<scenario_label>/<policy>/…
    Repeats remove cluster noise; the report averages over them.
  • Idempotent / resumable per (run, scenario, policy), like today.

Scenario label

Extend the label to encode target service and spike params, e.g. rate_rps=1200__fault_duration=30__fault_rate=cartservice-90pct__spikes=2__gap=60 and rate_rps=1000__fault_duration=30__fault_rate=productcatalogservice-75pct. Only the driver and the report builder parse this — not the viewer.

Part 4 — HTML Report (build_proto_report.py)

A Python builder that reads outputs/proto-report/<sweep_ts>/run{1,2,3}/…, averages across the 3 repeats, applies the sustained-recovery classification, and writes:

outputs/proto-report/<sweep_ts>/report.html
outputs/proto-report/<sweep_ts>/assets/        # PNG charts + per-scenario CSVs

Inputs & averaging

  • Reads each run{1,2,3}/<scenario>/<policy>/’s timeline.json, client-metrics/*.csv, resource-usage.csv, summary.csv directly (self-contained; no timeseries.json / viewer dependency).
  • Per-second curves (goodput, success rate, total RPS, latency pXX, retry amplification, cart/RL pod CPU/mem) are aligned on t − fault_start and averaged bucket-wise across the 3 runs (mean line + shaded min/max or ±std band).
  • Scalar metrics (sustained_recovery_sec per spike, amplification, final goodput ratio) reported as mean ± std over the 3 runs.

Report structure

  1. Summary matrix — 30 scenarios × 4 policies, each cell showing the recovered_twice / recovered_once / metastable label + mean sustained-recovery time, color-coded.
  2. New-metric vs old-metric comparison — where the old recovery_sec said “recovered” but sustained says otherwise (the headline correction).
  3. Per-scenario detail — averaged goodput / success-rate / latency / amplification charts with fault band(s) and per-spike recovery markers; one panel per metric, 4 policy lines.
  4. Multi-spike focus — MS1–MS3 side-by-side: did each policy recover once? twice?
  5. Alt-service focus — AS1/AS2 vs the comparable cart scenario (topology effect).

Part 5 — Two-Phase Execution

Phase A — First analysis on EXISTING data do first

No new cluster runs. Build the helper + report builder and run them over data we already have, to validate the metric and the report format:

  • Source: outputs/prototype-new/full-sweep/20260517_002700/ (25 scenarios; provides no-control, envoy-retry-budget, arolla) and outputs/prototype-new/rb-rl-v5/<ts>/ (rb-rl-v5, only the 2 scenarios it covers).
  • Report covers the existing scenarios only; rb-rl-v5 appears where present, the new 5 scenarios are absent (no data yet). Averaging degrades to single-run (n=1) since the old sweep was run once.
  • Deliverable: outputs/proto-report/first-analysis/report.html for the researcher to confirm the metric behaves and the report layout is right.
Phase A is a methodology + format dry-run. Its numbers are single-run and partial; it exists to get sign-off before spending cluster time.

Phase B — Full re-run after confirmation after sign-off

  • Run all 30 scenarios × 4 policies × 3 repeats into outputs/proto-report/<sweep_ts>/run{1,2,3}/ (preceded by the mandatory warm-up sweeps and Arolla wasm server from CLAUDE.md).
  • Regenerate the report with real 3-run averaging.

Runtime estimate (Phase B)

  • Cart single-spike (avg FD ~45): ~325 s/policy × 4 ≈ 22 min/scenario × 25 ≈ 9 h.
  • Multi-spike (FD + gap): ~430 s/policy × 4 ≈ 29 min × 3 ≈ 1.4 h.
  • Alt-service: ~22 min × 2 ≈ 0.7 h.
  • ≈ 11 h per repeat × 3 ≈ ~33 h of cluster wall-clock (plus warm-ups). Plan for a long-lived tmux session; the driver’s resumability covers interruptions.
